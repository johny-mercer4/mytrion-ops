01

Operating model

These rules apply to every route, repository, integration, job, and realtime event.

Every operation gets a budget

  • Deadline and cancellation signal.
  • Maximum rows, bytes, provider calls, and retries.
  • Separate interactive, background, write, and export concurrency.
  • Fail predictably before a dependency exhausts the whole process.

Preferred read hierarchy

  1. Authorized local projection or cache.
  2. Application PostgreSQL repository.
  3. Prepared DWH mart or cached aggregate.
  4. External provider only on miss, explicit refresh, or sync.

Preferred write hierarchy

Transaction → domain update → outbox → commit → worker → provider.

Never hold a database transaction open while calling Zoho, DWH, object storage, messaging, or another network service.

Forbidden patterns

  • One upstream query per card or table row.
  • Unbounded list endpoints or retry loops.
  • Cross-tenant cache keys.
  • Blind full-page refetch after a one-row update.
  • Logging secrets or complete vendor payloads.

Zoho CRM: choose the correct API

COQL is the default for filtered relational reads—not a universal replacement for purpose-built APIs.

NeedUseReason / control

COQL discipline

  • Select only necessary fields and use live API names.
  • Order by Modified_Time,id or another stable pair.
  • Prefer keyset criteria over growing offsets.
  • Batch relationships; never query per UI record.
  • Beyond 100k matching rows, move to Bulk Read.

Credit and concurrency governor

  • One semaphore per Zoho org and application.
  • Reserve slots for interactive traffic.
  • Track estimated credits and X-API-CREDITS-REMAINING.
  • Heavy API sub-concurrency must remain below ten.
  • Honor 429 and Retry-After; jitter transient retries.

Write safety

Use idempotency in Mytrion plus Zoho duplicate_check_fields. Parse per-record success/failure. A timeout after sending is an unknown outcome: reconcile by stable external ID before retrying.

Sync model

Zoho notifications enqueue small sync jobs. Workers update a local projection and publish invalidation. Periodic watermark reconciliation repairs missed or delayed notifications.

04

DWH PostgreSQL

A bounded, read-only analytical source—not a transactional backend or per-card API.

Query contract

  • Read-only database role plus session enforcement.
  • PostgreSQL $1 placeholders.
  • Filter and aggregate in SQL; return bounded rows.
  • Batch IDs with ANY($1).
  • Prepared marts for recurring interactive metrics.

Capacity

The current small pool and 30-second statement timeout are sensible. Keep application concurrency below pool capacity so health checks and interactive queries retain a slot. Coalesce identical in-flight queries.

Freshness and failure

Every analytical response should carry generatedAt, sourceHealth, partial, and freshness. Serve an authorized stale snapshot when DWH or dbt is temporarily unavailable.

Do not

  • Write or migrate the third-party DWH.
  • Open distributed transactions with the app DB.
  • Run one query per customer/card.
  • Use SELECT * or return raw fact tables to browsers.
  • Use plaintext transport outside a trusted private network.
05

Application PostgreSQL

The durable transactional authority for Mytrion-owned state, audit, idempotency, outbox, and projections.

Global connection budget

(API instances × API pool)
+ (worker instances × pg-boss pool)
+ migrations + monitoring + admin reserve
< database max_connections

Measure pool wait before increasing pool size. More connections can reduce throughput through memory pressure and context switching.

Interactive query standard

  • 2–5 second statement budget.
  • 1–2 second lock budget.
  • Short idle-in-transaction limit.
  • Cursor pagination with stable tie-breaker.
  • Composite index begins with tenant and supports filter + sort.

Write standard

  • Repository-only DB access with tenant_id.
  • Optimistic version checks.
  • Unique idempotency constraint.
  • Audit and outbox in the same transaction.
  • Return the updated representation; invalidate narrowly.

Operational hygiene

  • pg_stat_statements and slow-query sampling.
  • Monitor locks, dead tuples, bloat, temp files, and pool wait.
  • Use EXPLAIN (ANALYZE, BUFFERS) in staging.
  • Create large indexes concurrently when safe.
  • Test PITR restoration, not only backup creation.

Current hardening priority

Managed PostgreSQL currently disables certificate identity verification. Replace rejectUnauthorized:false with verified TLS/CA handling. Add route-class statement and lock timeouts instead of relying on an unlimited application query.

06

PgVector and retrieval

Optimize for authorization, recall, latency, and index memory—not nearest-neighbor latency alone.

Current direction

HNSW cosine indexing, tenant/audience indexes, department filtering, and a GIN text-search leg form a sound hybrid base.

Query controls

  • Use the matching cosine operator <=>.
  • Apply tenant and audience authorization inside SQL.
  • Benchmark exact search for very small authorized subsets.
  • Tune hnsw.ef_search against measured recall.
  • Use iterative scans when post-filtering under-returns.

Embedding lifecycle

  • Deterministic content hash skips unchanged chunks.
  • Version model, dimensions, chunker, and source revision.
  • Embed asynchronously in bounded batches.
  • Activate new revisions atomically.
  • Retire old vectors asynchronously.

Scale signals

Track index RAM, vector count, insert/update rate, p95 search latency, and offline recall@k. Partitioning, partial indexes, halfvec, or a separate vector service require evidence—not record count alone.

pg-boss jobs

Queue separation is resource isolation. Job delivery does not replace domain idempotency.

Queue classConcurrencyBehavior
zoho-readBelow org/provider ceilingWatermark sync, metadata refresh, bulk-read coordination.
zoho-writeLower and reservedIdempotent external writes; reconcile unknown outcomes.
dwh-heavyBelow DWH pool capacityExports and expensive aggregation; never starve interactive reads.
embeddingProvider/token boundedHash-deduplicated batches with versioned results.
notificationsLatency optimizedSmall payloads, quick acknowledgement, durable follow-up.
exportsCPU/memory boundedObject-storage output, progress, cancellation, expiry.

Production topology

API processes use send-only mode. Dedicated worker processes own consumers and schedules. This protects HTTP latency and lets worker classes scale independently.

Job contract

  • Small schema-versioned payload.
  • Domain idempotency key.
  • Timeout, retry limit, exponential backoff, jitter.
  • Dead-letter queue and operator runbook.
  • Correlation ID from request through provider call.

Never retry

Validation failures, missing permissions, revoked credentials, malformed input, or deterministic conflicts. Retrying permanent errors converts one failure into a queue outage.

Observe

Queue depth, oldest-job age, processing p95, success rate, retry rate, dead letters, schedule lag, stuck-active jobs, and pool utilization.

08

WebSocket and pub/sub

WebSocket transports authorized hints. Durable state and replay live elsewhere.

Connection standard

  • One connection per browser session.
  • Authenticate the handshake and periodically revalidate.
  • Authorize every subscription to tenant/user/department rooms.
  • Heartbeat, idle timeout, payload cap, and connection cap.
  • Exponential reconnect with jitter and resume cursor.

Event envelope

{
  "id": "evt_…",
  "type": "ticket.updated.v1",
  "tenantId": "…",
  "subjectId": "…",
  "version": 42,
  "occurredAt": "…"
}

Send IDs and versions, not sensitive complete records. Clients invalidate or patch authorized cached state.

PostgreSQL LISTEN/NOTIFY

Good for lightweight same-database invalidation at small scale. Notifications are delivered after commit, payloads are under 8 KB by default, and disconnected consumers cannot replay them. Send a durable event ID, not the data itself.

Redis Pub/Sub

Use for cross-instance fan-out and cache invalidation. Redis Pub/Sub is at-most-once: pair it with an outbox, Redis Streams, or another durable log when replay and guaranteed processing matter.

Other external vendors

Every provider uses one adapter contract, even when its authentication and limits differ.

Required adapter capabilities

timeoutcancellationconcurrency semaphorecredit/rate telemetrybounded retrycircuit breakerredactionhealthidempotencymock contract

Communications

RingCentral, Gong, Telegram: deduplicate provider events/calls, verify webhooks, retain provider IDs, pause polling when hidden, and lazy-load recordings or transcripts.

Business systems

Zoho Desk/People/WorkDrive, Power BI, ServerCRM: keep purpose-specific scopes, cache metadata, separate reads/writes, expose source health, and avoid browser-owned credentials.

Files and automation

S3/EFS/Dropbox/Zapier: presigned short-lived access, private-by-default buckets, checksum and size validation, malware scanning, lifecycle expiry, webhook replay protection.

External databases

AWS RDS/Aurora and future SQL providers use a dedicated, bounded, TLS-verified pool and a server-enforced read-only role by default. Prefer IAM database authentication where operationally supported. PostgreSQL uses $1 placeholders; MySQL uses ?.

AI and embedding providers

Batch by token and payload limits, cap concurrent generations, record model/version/cost, redact sensitive prompts, and never retry non-idempotent generations blindly. Cache only when authorization and data-retention policy permit it.

Retry classification

Retry: connection reset, timeout before send, 429 with delay, 502/503/504.
Do not retry: 400/401/403/404 validation or permission failures.
Reconcile first: timeout after a write may have reached the provider.

Universal response metadata

{ "freshness": "fresh|stale",
  "generatedAt": "ISO timestamp",
  "sourceHealth": { "zoho": "ok" },
  "partial": false,
  "requestId": "…" }

Security baseline

Tenant isolation, least privilege, verified transport, controlled writes, and recoverability are release gates.

Identity and authorization

  • RBAC checked at route and tool dispatcher.
  • Repositories enforce tenant_id.
  • Effective “View as” identity enters authorization and cache keys.
  • RLS protects sensitive tables in depth.
  • Admin writes require explicit risk classification and audit.

Transport and secrets

  • TLS with certificate verification.
  • Secrets in a managed secret store, never source or logs.
  • Least-privilege OAuth scopes and periodic token rotation.
  • Separate runtime, migration, worker, and read-only DB users.
  • Private networking for databases where possible.

Webhooks and files

  • Signature/token validation and timestamp window.
  • Replay/idempotency key persisted before processing.
  • Body-size limits before parsing.
  • File MIME, extension, checksum, size, and malware checks.
  • Presigned access expires and is audience-scoped.

Data protection

  • Structured log allowlist and payload redaction.
  • Retention and deletion policies by data class.
  • Encrypted backups and restore drills.
  • Cross-tenant leakage tests before feature work.
  • Security alerts for repeated denial, replay, and credential failure.

Scaling stages

Advance when measurements cross a boundary; do not add distributed systems speculatively.

StageTopologyRequired controlsMove on when…
1 · Controlled monolithOne API, one worker or bounded inline jobs, process cache, PostgreSQL.Strict pools, in-flight dedupe, SWR, idempotency, query and provider metrics.Need high availability, worker contention affects HTTP, or a second API instance is required.
2 · Separated computeMultiple API nodes, dedicated workers, Redis cache/pub-sub, shared PostgreSQL.Distributed cache keys, outbox fan-out, send-only APIs, connection budget, graceful rolling deploys.DB connection pressure, hot-table contention, queue backlog, or read-heavy analytical load dominates.
3 · Data specializationPgBouncer, read replicas where consistency allows, prepared marts, worker autoscaling, object exports.Replica-lag awareness, queue-based autoscaling, cache stampede protection, partition/bloat operations.Measured PostgreSQL write/storage ceilings or independent regional/compliance requirements.
4 · Service extractionExtract only proven bounded domains.Durable event contracts, ownership, SLOs, tracing, independent capacity and failure isolation.A domain needs materially different scale, security, deploy cadence, or data ownership.

Scale by bottleneck

HTTP nodes, workers, DWH, Zoho concurrency, PostgreSQL connections, vector memory, and WebSocket connections scale differently. A single “add more instances” control can make database and provider pressure worse.

Production release checklist

A short gate to use on every feature and integration change.

Data

  • All app DB access is in a tenant-scoped repository.
  • Pagination is bounded and stable.
  • Indexes match production filters and sort.
  • Migration and rollback behavior are understood.
  • No external network call occurs inside a transaction.

Provider

  • Timeout, cancellation, semaphore, retry class, and circuit breaker exist.
  • Write is idempotent or reconciles uncertain outcomes.
  • 429 and partial success are tested.
  • Cache/freshness/source health are represented.
  • OAuth scopes and payload logging are minimized.

Jobs and realtime

  • Queue, concurrency, timeout, retry, DLQ, and runbook exist.
  • Payload is small and schema-versioned.
  • Realtime event is authorized and versioned.
  • Reconnect/replay path is tested.
  • Background load cannot starve interactive traffic.

Verification

  • Lint, typecheck, tests, and cross-tenant tests pass.
  • Cold, warm, stale, provider-down, and rate-limited states pass.
  • Load test includes realistic provider and DB ceilings.
  • Dashboards and alerts are live before rollout.
  • Rollback and database restore paths are known.
